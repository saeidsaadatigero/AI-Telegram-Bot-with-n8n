# معماری پروژه ربات تلگرام هوشمند با n8n

این سند، معماری فنی پروژه و مفاهیم پایه‌ای n8n را که در آن به کار رفته‌اند توضیح می‌دهد. هدف آن هم ارائه به کارفرما و هم استفاده به عنوان منبع آموزشی است.

---

## ۱. مفهوم Workflow در n8n

**n8n** یک پلتفرم اتوماسیون گردش‌کار مبتنی بر گره (Node-based) است. واحد اصلی کار در آن **Workflow** نام دارد.

یک Workflow مجموعه‌ای از **گره‌ها (Nodes)** است که با **اتصال‌ها (Connections)** به هم وصل شده‌اند و داده از یکی به دیگری جریان پیدا می‌کند.

### مدل داده

داده در n8n همیشه به شکل **آرایه‌ای از آیتم‌ها** جابه‌جا می‌شود. هر آیتم یک شیء JSON است:

```json
[
  { "json": { "message": { "text": "سلام", "chat": { "id": 12345 } } } }
]
```

نکته کلیدی: اگر گره‌ای ۵ آیتم به گره بعدی بدهد، گره بعدی **۵ بار** اجرا می‌شود (یک بار برای هر آیتم). این رفتار در n8n «Item Linking» نامیده می‌شود و پایه فهم رفتار Workflow هاست.

### دسترسی به داده با Expression

n8n یک زبان عبارت‌نویسی (Expression) بر پایه JavaScript دارد که داخل `{{ }}` نوشته می‌شود:

| الگو | کاربرد |
|---|---|
| `{{ $json.field }}` | خواندن فیلدی از آیتم فعلی (خروجی گره قبلی) |
| `{{ $('Node Name').item.json.field }}` | خواندن داده از هر گره دلخواه در Workflow، حتی غیرمجاور |
| `{{ $env.VAR_NAME }}` | خواندن متغیر محیطی سیستم |
| `{{ $now }}` | زمان جاری |

در این پروژه، گره `Send Reply` مستقیماً به گره `Telegram Trigger` وصل نیست (بین آن‌ها `AI Agent` قرار دارد)، بنابراین برای گرفتن شناسه چت از الگوی دوم استفاده شده است:

```javascript
{{ $('Telegram Trigger').item.json.message.chat.id }}
```

این یکی از مهم‌ترین نکاتی است که تازه‌کاران n8n در آن اشتباه می‌کنند: بعد از عبور داده از گره AI، شیء اصلی پیام تلگرام دیگر در `$json` وجود ندارد.

## ۲. تفاوت Trigger Node و Action Node

| ویژگی | Trigger Node | Action Node |
|---|---|---|
| نقش | نقطه **شروع** Workflow | انجام یک **عملیات** روی داده |
| تعداد در Workflow | حداقل یکی لازم است | هر تعداد |
| ورودی | ندارد (شکل گره در بوم گرد است) | خروجی گره قبلی |
| نمونه در این پروژه | `Telegram Trigger`، `Error Trigger` | `AI Agent`، `Send Reply`، `Alert Admin` |

### انواع Trigger

۱. **Webhook / App Trigger** — با یک رویداد خارجی فعال می‌شود (مثل `Telegram Trigger` که با پیام کاربر اجرا می‌شود). این نوع، **رویدادمحور (Event-driven)** است و تأخیر تقریباً صفر دارد.
۲. **Schedule Trigger** — در بازه‌های زمانی مشخص اجرا می‌شود (Cron).
۳. **Manual Trigger** — با کلیک روی دکمه اجرا در محیط توسعه.
۴. **Error Trigger** — تنها زمانی اجرا می‌شود که Workflow دیگری با خطا مواجه شود.

در این پروژه از نوع اول و چهارم استفاده شده است.

### زیرگره (Sub-node) — مفهوم ویژه در گره‌های AI

گره‌های خانواده LangChain در n8n مفهوم جدیدی به نام **Sub-node** دارند. این گره‌ها به جای اینکه در جریان افقی داده قرار بگیرند، از **پایین** به گره اصلی متصل می‌شوند و یک قابلیت را در اختیار آن می‌گذارند:

```
        ┌──────────────┐
 main ─►│   AI Agent   │─► main
        └──────┬───────┘
               │ ai_languageModel
        ┌──────┴────────────┐
        │ OpenAI Chat Model │   ← زیرگره (Sub-node)
        └───────────────────┘
```

در فایل JSON این پروژه، این اتصال با نوع `ai_languageModel` در بخش `connections` مشخص شده است — نه با نوع معمول `main`. سایر زیرگره‌های قابل اتصال به یک Agent عبارت‌اند از `ai_memory` (حافظه گفتگو)، `ai_tool` (ابزارها) و `ai_outputParser` (تبدیل خروجی به ساختار مشخص).

## ۳. نحوه اتصال n8n به سرویس‌های خارجی

### اتصال به تلگرام (ورودی — مدل Webhook)

هنگام **فعال (Active)** شدن Workflow، گره `Telegram Trigger` به صورت خودکار متد `setWebhook` را روی Bot API تلگرام صدا می‌زند و آدرس عمومی n8n را به تلگرام معرفی می‌کند. از آن پس، هر پیام کاربر بلافاصله به شکل یک درخواست `POST` به n8n ارسال می‌شود.

```
کاربر → سرورهای تلگرام → POST به آدرس Webhook → n8n → اجرای Workflow
```

**پیامد عملی:** روی `localhost` این جریان کار نمی‌کند، چون سرورهای تلگرام نمی‌توانند به ماشین شما دسترسی داشته باشند. راه‌حل‌ها: استفاده از Test URL در حالت توسعه، تونل عمومی مانند `ngrok`، یا استقرار n8n روی یک سرور با دامنه و HTTPS معتبر.

### اتصال به OpenAI (خروجی — مدل REST)

گره `OpenAI Chat Model` یک درخواست `POST` به `https://api.openai.com/v1/chat/completions` می‌فرستد و کلید API را در هدر `Authorization` قرار می‌دهد. این ارتباط **خروجی** است و نیازی به آدرس عمومی ندارد؛ به همین دلیل بخش هوش مصنوعی حتی روی `localhost` هم کاملاً کار می‌کند.

### جمع‌بندی جهت ارتباط

| سرویس | جهت | نیاز به IP عمومی |
|---|---|---|
| تلگرام (دریافت پیام) | ورودی — Webhook | بله |
| تلگرام (ارسال پاسخ) | خروجی — REST | خیر |
| OpenAI | خروجی — REST | خیر |

## ۴. مدیریت خطا

این پروژه از **دو لایه** مدیریت خطا استفاده می‌کند؛ این تفکیک، تفاوت یک Workflow نمایشی با یک Workflow عملیاتی است.

### لایه اول: خطای در سطح گره (`onError`)

گره `AI Agent` با تنظیم `onError: continueErrorOutput` یک **خروجی دوم (قرمز)** پیدا می‌کند. اگر فراخوانی OpenAI شکست بخورد (اتمام اعتبار، Timeout، محدودیت نرخ)، به جای توقف کل Workflow، داده به شاخه خطا می‌رود و گره `Notify User On Failure` یک پیام مؤدبانه به کاربر می‌فرستد.

مزیت: **کاربر هرگز بدون پاسخ نمی‌ماند.**

```
AI Agent ─┬─(موفق)─► Send Reply
          └─(خطا)──► Notify User On Failure
```

### لایه دوم: خطای در سطح Workflow (`Error Trigger`)

اگر خطایی رخ دهد که در هیچ گره‌ای مدیریت نشده باشد (مثلاً توکن تلگرام باطل شود)، n8n اجرا را متوقف و **Error Workflow** تعیین‌شده در تنظیمات را اجرا می‌کند. گره `Error Trigger` این رویداد را می‌گیرد و شیئی با این ساختار تحویل می‌دهد:

```json
{
  "execution": {
    "id": "231",
    "error": { "message": "...", "stack": "..." },
    "lastNodeExecuted": "Send Reply",
    "mode": "webhook"
  },
  "workflow": { "id": "1", "name": "AI Telegram Bot" }
}
```

گره `Alert Admin` این اطلاعات را قالب‌بندی کرده و برای ادمین در تلگرام می‌فرستد؛ یعنی **مانیتورینگ بدون نیاز به سرویس جانبی**.

> برای فعال شدن این لایه، باید در `Workflow Settings → Error Workflow` همین Workflow انتخاب شود.

### گزینه‌های تکمیلی مدیریت خطا در n8n

- `retryOnFail` به همراه `maxTries` و `waitBetweenTries` — برای خطاهای گذرای شبکه
- `continueOnFail` — ادامه اجرا با نادیده گرفتن خطا (برای عملیات غیرحیاتی)
- گره `Stop and Error` — ایجاد عمدی خطا هنگام نامعتبر بودن داده ورودی

## ۵. امنیت با Credential

n8n اطلاعات حساس را از منطق Workflow جدا نگه می‌دارد:

| ویژگی | توضیح |
|---|---|
| **ذخیره‌سازی رمزنگاری‌شده** | اعتبارنامه‌ها با کلید `N8N_ENCRYPTION_KEY` در پایگاه‌داده داخلی رمزنگاری می‌شوند |
| **جدایی از Workflow** | هنگام Export، فقط **نام و شناسه** اعتبارنامه در JSON نوشته می‌شود، نه مقدار کلید |
| **استفاده مجدد** | یک اعتبارنامه `telegram_bot` در هر چهار گره تلگرام این پروژه به کار رفته است |
| **تعویض متمرکز** | با تغییر کلید در یک نقطه، همه گره‌ها به‌روز می‌شوند |

به همین دلیل، فایل `workflow/telegram_ai_bot.json` این مخزن می‌تواند با خیال راحت روی گیت‌هاب منتشر شود — هیچ کلیدی در آن نیست.

### لایه‌های امنیتی این پروژه

۱. **`.env`** — نگهداری متغیرهای محیطی، خارج از کنترل نسخه (در `.gitignore`).
۲. **`.env.example`** — فقط ساختار متغیرها بدون مقدار واقعی، برای مستندسازی.
۳. **Credential Manager** — نگهداری رمزنگاری‌شده کلیدها داخل n8n.
۴. **Docker Volume** — پایگاه‌داده رمزنگاری‌شده در `n8n_data` باقی می‌ماند و در مخزن قرار نمی‌گیرد.

## ۶. زیرساخت اجرا (Docker)

فایل `docker-compose.yml` سرویس n8n را با این مشخصات بالا می‌آورد:

| بخش | نقش |
|---|---|
| `image: n8nio/n8n:latest` | ایمیج رسمی n8n |
| `ports: 5678:5678` | انتشار پنل مدیریت روی `http://localhost:5678` |
| `env_file: .env` | تزریق متغیرهای محیطی بدون قرار دادن آن‌ها در فایل Compose |
| `volumes: n8n_data:/home/node/.n8n` | ماندگاری Workflow ها، اعتبارنامه‌ها و تاریخچه اجراها پس از ری‌استارت |
| `volumes: ./workflow:/home/node/workflow` | امکان import فایل JSON از طریق CLI داخل کانتینر |
| `restart: unless-stopped` | بالا آمدن خودکار پس از ری‌استارت سیستم |

**نکته ویندوز:** روی Docker Desktop با بک‌اند WSL2، حالت `--network=host` پشتیبانی نمی‌شود. به همین دلیل در این پروژه از انتشار عادی پورت (`ports`) استفاده شده که هم روی ویندوز و هم روی لینوکس بدون تغییر کار می‌کند.

## ۷. جریان کامل اجرا (گام‌به‌گام)

۱. کاربر در تلگرام پیام «n8n چیست؟» را ارسال می‌کند.
۲. سرور تلگرام یک درخواست `POST` به آدرس Webhook گره `Telegram Trigger` می‌فرستد.
۳. n8n یک Execution جدید می‌سازد و آیتم ورودی را تولید می‌کند: `{ message: { text, chat: { id } } }`.
۴. گره `AI Agent` مقدار `{{ $json.message.text }}` را به عنوان پرسش و پرامپت سیستم فارسی را به عنوان دستور نقش، به زیرگره `OpenAI Chat Model` می‌دهد.
۵. زیرگره درخواست را به OpenAI ارسال و پاسخ را دریافت می‌کند.
۶. گره `AI Agent` نتیجه را در فیلد `output` قرار می‌دهد.
۷. گره `Send Reply` با استفاده از `{{ $('Telegram Trigger').item.json.message.chat.id }}` پاسخ را به همان چت بازمی‌گرداند.
۸. اگر مرحله ۵ شکست بخورد، جریان به `Notify User On Failure` منحرف می‌شود.
۹. اگر خطای مدیریت‌نشده‌ای رخ دهد، `Error Trigger` فعال شده و `Alert Admin` گزارش را برای ادمین می‌فرستد.

## ۸. ملاحظات مقیاس‌پذیری برای محیط عملیاتی

| موضوع | راهکار |
|---|---|
| **پایگاه‌داده** | جایگزینی SQLite پیش‌فرض با PostgreSQL از طریق متغیرهای `DB_TYPE` و `DB_POSTGRESDB_*` |
| **حالت صف** | فعال‌سازی `EXECUTIONS_MODE=queue` به همراه Redis و چند Worker برای پردازش موازی |
| **امنیت شبکه** | قرار دادن n8n پشت Reverse Proxy (Nginx / Traefik) با گواهی HTTPS |
| **کنترل هزینه** | تعیین `maxTokens`، انتخاب مدل ارزان‌تر، و محدودسازی نرخ درخواست هر کاربر |
| **پاک‌سازی داده** | تنظیم `EXECUTIONS_DATA_MAX_AGE` برای حذف خودکار تاریخچه اجراهای قدیمی |
| **حافظه گفتگو** | افزودن زیرگره `Window Buffer Memory` با کلید نشست بر پایه `chat.id` |

## ۹. Webhook در برابر Polling

انتخاب میان این دو الگو، یکی از تصمیم‌های معماری مهم در ساخت ربات‌هاست.

### الگوی Webhook (Push)

سرویس بیرونی هنگام رخ دادن رویداد، خودش به ما درخواست می‌فرستد.

```
تلگرام ──POST──► n8n
```

- **مزیت:** تأخیر تقریباً صفر، مصرف منابع فقط هنگام وجود پیام.
- **محدودیت:** n8n باید یک آدرس عمومی HTTPS داشته باشد. روی `localhost` این الگو **بی‌صدا شکست می‌خورد**: متد `setWebhook` موفق ثبت نمی‌شود یا آدرس غیرقابل‌دسترس ثبت می‌شود، تلگرام پیام‌ها را در صف نگه می‌دارد و کاربر هیچ خطایی نمی‌بیند.

بررسی وضعیت واقعی همیشه با این فراخوانی انجام می‌شود:

```bash
curl "https://api.telegram.org/bot<TOKEN>/getWebhookInfo"
```

اگر `"url": ""` برگردد یعنی هیچ Webhook‌ای ثبت نشده و `pending_update_count` تعداد پیام‌های معطل‌مانده را نشان می‌دهد.

### الگوی Polling (Pull)

ما در بازه‌های منظم از سرویس بیرونی می‌پرسیم «چیز جدیدی هست؟»

```
n8n ──GET getUpdates──► تلگرام
```

- **مزیت:** فقط به ارتباط **خروجی** نیاز دارد؛ پشت NAT، فایروال یا روی `localhost` بدون هیچ تونلی کار می‌کند.
- **محدودیت:** تأخیر به اندازه بازه زمان‌بند، و مصرف درخواست حتی وقتی پیامی نیست.

### مسئله مدیریت وضعیت (State)

الگوی Polling برخلاف Webhook **بدون‌حالت نیست**؛ باید به خاطر بسپاریم آخرین پیام پردازش‌شده کدام بوده، وگرنه در هر اجرا همان پیام‌ها دوباره پردازش می‌شوند.

n8n برای این کار حافظه دائمی در سطح Workflow دارد:

```javascript
const staticData = $getWorkflowStaticData('global');
staticData.telegramOffset = update.update_id + 1;
```

این مقدار در پایگاه‌داده n8n ذخیره می‌شود و بین اجراها باقی می‌ماند — اما **فقط در اجرای Production**. در اجرای دستی (Execute Workflow) تغییرات ذخیره نمی‌شود؛ این یکی از رایج‌ترین دام‌های تازه‌کاران است.

از سمت تلگرام، ارسال `offset = update_id + 1` علاوه بر فیلتر کردن، آن پیام را در صف سرور تلگرام نیز **تأیید (ACK)** می‌کند و حذف می‌نماید.

### جمع‌بندی انتخاب

| محیط | الگوی پیشنهادی |
|---|---|
| توسعه محلی روی `localhost` | Polling |
| سرور با دامنه و HTTPS معتبر | Webhook |
| پشت NAT یا فایروال سازمانی | Polling |
| نیاز به کمترین تأخیر ممکن | Webhook |

هر دو نسخه در این مخزن پیاده‌سازی شده‌اند و **بخش هوش مصنوعی آن‌ها کاملاً یکسان است**؛ تنها گره ورودی و روش ارسال پاسخ تفاوت دارد. این نشان می‌دهد که لایه منطق را می‌توان مستقل از لایه انتقال طراحی کرد.
